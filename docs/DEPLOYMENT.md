# การ deploy Mindful Practice

เอกสารนี้เขียนให้คนที่ต้องมา deploy หรือดูแลโปรเจกต์นี้ต่อ โดยไม่ต้องถามเจ้าของเดิม

ตัดสินใจเมื่อ: 20 กันยายน 2569

## 1. ภาพรวมสถาปัตยกรรม

```
GitHub (source of truth)
      │  push
      ▼
Cloudflare Pages  ──build──▶  Production PWA
                                   │
                                   ▼
                          iPhone / มือถือของผู้ใช้
                                   │
                                   ▼
                    ประวัติการฝึกอยู่ใน IndexedDB ของเครื่องนั้น
```

แอปนี้เป็น **static ล้วน**: ไม่มี backend, ไม่มีฐานข้อมูลฝั่งเซิร์ฟเวอร์, ไม่มี login, ไม่มี analytics, ไม่มีการติดตามผู้ใช้

**ไม่มีข้อมูลการฝึกของผู้ใช้ถูกส่งไปที่ Cloudflare หรือ GitHub** ทั้งสองที่เห็นแค่โค้ดกับไฟล์ static เท่านั้น

## 2. บทบาทของ GitHub

GitHub เป็นแหล่งจริงถาวรของโปรเจกต์ ใช้เก็บ source code, ประวัติการแก้, เอกสาร, release ที่ติดป้ายเวอร์ชัน และเป็นต้นทางของการ deploy

ตั้งใจให้ repository อยู่ในสภาพที่เปิดสาธารณะได้ ถ้าวันหนึ่งตัดสินใจว่าการเก็บรักษาระยะยาวและการให้คนอื่นสานต่อมีค่ากว่าการปิดไว้

## 3. บทบาทของ Cloudflare Pages

เป็น **โฮสต์หลักของ production** เหตุผลที่เลือกแทน GitHub Pages: คำขอไฟล์ static ของ Cloudflare Pages **ฟรีและไม่จำกัดจำนวน** ตราบใดที่ไม่มีการเรียก Pages Functions ส่วน GitHub Pages มีเพดาน bandwidth แบบ soft limit ซึ่งเป็นปัญหาถ้าวันหนึ่งแจกให้คนใช้จำนวนมาก

เพดานของแพ็กเกจฟรีที่ต้องไม่ชน:

| ข้อจำกัด | เพดาน | สถานะปัจจุบัน |
|---|---|---|
| build ต่อเดือน | 500 | ใช้ไม่กี่ครั้ง |
| จำนวนไฟล์ต่อไซต์ | 20,000 | **18 ไฟล์** |
| ขนาดไฟล์เดี่ยว | 25 MiB | **ใหญ่สุด 0.38 MiB** |
| คำขอไฟล์ static | ฟรีไม่จำกัด | — |

**ห้ามเพิ่ม Pages Functions, Workers หรือ logic ฝั่งเซิร์ฟเวอร์** นอกจากมีความจำเป็นที่ชัดเจนในอนาคต เพราะสิ่งเหล่านี้จะทำให้คำขอปกติกลายเป็นการเรียก Functions ซึ่งมีโควตาและค่าใช้จ่าย

## 4. ทำไมไม่ใช้ Railway

Railway เป็นมาตรฐานของโปรเจกต์อื่นในบ้านนี้ แต่**ไม่เหมาะกับแอปนี้** เพราะ Railway มีไว้สำหรับแอปที่มี server runtime ทำงานตลอดเวลา ส่วน Mindful Practice ไม่มี backend ให้รันเลย การใช้ Railway จะเพิ่มค่าใช้จ่ายรายเดือนโดยไม่ได้อะไรกลับมา

หลักการของโปรเจกต์นี้คือ **"แอปหลักต้องอยู่ได้ต่อไปโดยไม่ต้องมีบิลค่าเซิร์ฟเวอร์รายเดือน"**

เลี่ยงการผูกกับ Railway, ฐานข้อมูลแบบเสียเงิน, เซิร์ฟเวอร์ที่ต้องเปิดตลอด, โฮสต์แบบ subscription, ระบบยืนยันตัวตนฝั่งเซิร์ฟเวอร์ และบริการ backend เจ้าของเดียว

ถ้าวันหนึ่งเพิ่มฟีเจอร์ที่ใช้คลาวด์ **แอปหลักต้องยังใช้งานในเครื่องได้เหมือนเดิม** คือเปิดแอป อ่านบทสวด นั่งสมาธิ เดินจงกรม จับเวลา ดูประวัติและสถิติในเครื่องได้ แม้บริการคลาวด์ล่ม

## 7. ขั้นตอน deploy บน Cloudflare Pages

1. push โค้ดขึ้น GitHub
2. Cloudflare Dashboard → Workers & Pages → Create → Pages → Connect to Git → เลือก repository นี้
3. ตั้งค่า build:
   - **Framework preset:** None (หรือ Vite)
   - **Build command:** `npm run build`
   - **Build output directory:** `dist`
   - **Root directory:** ว่างไว้ (โปรเจกต์อยู่ที่รากของ repo)
4. Environment variables: **ไม่ต้องใส่** โปรเจกต์นี้ไม่มี secret
5. Save and Deploy

เวอร์ชัน Node อ่านจากไฟล์ `.node-version` ที่รากโปรเจกต์ (ตอนนี้คือ `22.12.0`) **ห้ามลบไฟล์นี้** เพราะ Vite 8 และ TypeScript 7 ต้องการ Node 20.19 ขึ้นไป ถ้า Cloudflare ใช้ Node เก่ากว่านั้น build จะล้ม

เพิ่ม custom domain ทีหลังได้จากแท็บ Custom domains ของโปรเจกต์ Pages

### ไม่ต้องตั้ง redirect หรือ rewrite

แอปใช้ **hash routing** (`#/practice/sitting`) ทุกเส้นทางจึงเป็นไฟล์ `index.html` ไฟล์เดียว **การรีเฟรชหรือเปิดลิงก์ลึกจะไม่เกิด 404** และไม่ต้องมีไฟล์ `_redirects` ตรวจแล้วว่าเปิด `#/records` ซ้ำตอนออฟไลน์ยังได้หน้าถูกต้อง

## 8. นโยบายไฟล์เสียง

```
public/audio/
  bells/      ระฆังเริ่ม/ระหว่างฝึก/จบ — สั้น ถูก precache
  ambience/   เสียงบรรยากาศและ keepalive — โหลดตอนใช้
  prayers/    เสียงบทสวด — โหลดตอนใช้
```

ชื่อไฟล์เสียงบทสวดมาจาก `content/prayers/catalog.json` ฟิลด์ `audioFile` เช่น `itipiso.m4a`, `bahung.m4a`, `millionaire-chant.m4a`

**การสร้าง URL รวมไว้ที่เดียวคือ `prayerAudioUrl()` ใน `src/content/audio.ts`** หน้าจอไม่ประกอบ path เองเลย นี่คือเงื่อนไขที่ทำให้ย้ายไฟล์ไป object storage ภายหลังได้โดยไม่ต้องแก้ UI

เสียงระฆังและเสียงบรรยากาศสร้างขึ้นเองจาก `scripts/generate_audio.py` (ต้องมี ffmpeg) สคริปต์ seed คงที่ รันซ้ำได้ผลเหมือนเดิมทุกไบต์ ไม่มีไฟล์เสียงจากบุคคลอื่นในโปรเจกต์

## 9. ข้อจำกัดขนาดไฟล์ 25 MiB

Cloudflare Pages ปฏิเสธไฟล์เดี่ยวที่เกิน **25 MiB** ทั้ง deployment ตรวจก่อน push ได้ด้วย:

```bash
find dist -type f -size +25M
```

ถ้าไม่มีผลลัพธ์แปลว่าผ่าน ไฟล์เสียงบทสวดความยาว 10–15 นาทีที่บีบเป็น m4a คุณภาพพูดมักอยู่ราว 5–10 MiB จึงยังปลอดภัย แต่ต้องวัดจริงทุกครั้งที่เพิ่มไฟล์

## 10. แผนย้ายไปใช้ object storage ในอนาคต

**ยังไม่ต้องทำตอนนี้** ทำเมื่อเข้าเงื่อนไขข้อใดข้อหนึ่ง: มีไฟล์เสียงจำนวนมาก, มีไฟล์บันทึกยาว, มีไฟล์เกิน 25 MiB หรือมีสื่อรวมแล้วหนักจนไม่ควรอยู่ใน repo

```
GitHub → Cloudflare Pages ─┬─ HTML/CSS/JS/PWA/ข้อความ/ไอคอน/เสียงสั้น
                           └─ URL เสียง ──▶ Cloudflare R2
```

**วิธีย้ายเมื่อถึงเวลา:** อัปโหลดไฟล์ขึ้น R2 แล้วแก้ `audioFile` ใน `catalog.json` เป็น URL เต็ม เช่น `https://media.example.com/itipiso.m4a` — เท่านั้น เพราะ `prayerAudioUrl()` ตรวจว่าขึ้นต้นด้วย `http://` หรือ `https://` ไหม ถ้าใช่จะคืนค่านั้นตรง ๆ **ไม่ต้องแก้โค้ดหน้าจอสักบรรทัด**

ถ้าย้ายไป R2 อย่าลืมตั้ง CORS ให้อนุญาต origin ของ Pages เพราะแอปใช้ HEAD request ตรวจว่ามีไฟล์จริงก่อนแสดงตัวเล่น

## 11. พฤติกรรม PWA และ offline

Service worker (`public/sw.js`) ลงทะเบียนเฉพาะ production build เพื่อไม่ให้ cache รบกวนตอนพัฒนา

**สิ่งที่ถูก cache ตอนติดตั้ง** — ตรวจจริงแล้วได้ 10 รายการพอดี:

```
/  ·  /index.html  ·  /assets/*.js  ·  /assets/*.css
/audio/bells/start.m4a  ·  interval.m4a  ·  end.m4a
/icons/icon.svg  ·  /icons/apple-touch-icon.png  ·  /manifest.webmanifest
```

**สิ่งที่ไม่ถูก cache โดยตั้งใจ:** ทุกอย่างใต้ `/audio/` ที่ไม่ใช่ระฆัง คือเสียงบรรยากาศและเสียงบทสวด จะโหลดตอนกดใช้เท่านั้น ข้อความบทสวดถูก bundle เข้าไปใน JS อยู่แล้วจึงอ่านออฟไลน์ได้

ต่อไปถ้าจะให้ดาวน์โหลดเสียงยาวไว้ใช้ออฟไลน์ ให้ทำเป็นปุ่ม **"ดาวน์โหลดไว้ใช้ออฟไลน์"** ที่ผู้ใช้กดเอง ไม่ใช่ precache อัตโนมัติ

**ห้ามถือว่า cache ของเบราว์เซอร์เป็นที่เก็บถาวร** ระบบล้างได้ทุกเมื่อ ข้อมูลผู้ใช้จริงต้องอยู่ใน IndexedDB เท่านั้น

เวลาเปลี่ยนสิ่งที่ cache ต้องขยับเลข `CACHE_NAME` ใน `sw.js` (ตอนนี้ `mindful-practice-shell-v5`) ไม่งั้นเครื่องที่เคยติดตั้งจะใช้ของเก่าต่อ ตัว SW เรียก `skipWaiting()` และ `clients.claim()` แล้ว จึงอัปเดตให้เองเมื่อเปิดแอปครั้งถัดไป

## 12. ข้อมูลผู้ใช้อยู่ในเครื่อง

`IndexedDB` ชื่อฐานข้อมูล `mindful-practice` เป็นแหล่งจริงของ `PracticeSession`, `ChantSession`, `ActiveSession`, `Settings`, `LegacyBaseline`, `CustomPrayer` — ไม่มีบัญชีผู้ใช้ ไม่มีการซิงก์

**ข้อควรรู้ที่กระทบผู้ใช้โดยตรง: เบราว์เซอร์ผูกข้อมูลไว้กับ origin** `https://xxx.pages.dev` กับ `https://practice.example.com` คือคนละที่เก็บข้อมูล **การเปลี่ยนโดเมนหรือ URL เท่ากับผู้ใช้เริ่มจากศูนย์** ถ้าจะเปลี่ยนโดเมนต้องประกาศให้ผู้ใช้ส่งออกข้อมูลก่อน

## 13. การสำรองข้อมูลด้วย export/import

ในเมนูตั้งค่ามี **ส่งออกเป็นไฟล์ JSON · นำเข้าจากไฟล์สำรอง · ล้างประวัติทั้งหมด**

- รูปแบบไฟล์: `{ format: 'mindful-practice-backup', version: 1, exportedAt, settings, practiceSessions, chantSessions, customPrayers, legacyBaseline }`
- ชื่อไฟล์: `mindful-practice-YYYY-MM-DD.json`
- ตัวตรวจไฟล์อยู่ใน `src/data/backup.ts` เป็นฟังก์ชันบริสุทธิ์ ทดสอบได้โดยไม่ต้องมีเบราว์เซอร์
- มีแถวเสียแถวเดียวจะปฏิเสธทั้งไฟล์ ไม่นำเข้าบางส่วนเงียบ ๆ
- การนำเข้าคือการแทนที่ทั้งหมด และถามยืนยันพร้อมแสดงจำนวนของเดิมเทียบกับในไฟล์

ผู้ใช้เก็บและย้ายข้อมูลตัวเองได้โดยไม่ต้องพึ่งเซิร์ฟเวอร์ของเรา และไม่ต้องมีบัญชี

## 14. มิเรอร์บน GitHub Pages (ทางเลือก ยังไม่ทำ)

ใช้เป็น URL สำรองหรือทางออกฉุกเฉินได้ **แต่ไม่ควรเป็นโฮสต์หลักถ้ามีคนใช้เยอะ** เพราะเพดาน bandwidth

ถ้า deploy ที่รากของโดเมน (เช่น `username.github.io`) ใช้ `dist/` ชุดเดิมได้เลย

ถ้า deploy ใต้ subpath (เช่น `username.github.io/mindful-practice/`) **ต้องแก้หนึ่งจุด** คือสร้าง `vite.config.ts` ที่ราก:

```ts
import { defineConfig } from 'vite';
export default defineConfig({ base: './' });
```

เหตุผล: ตอนนี้ `dist/index.html` อ้างไฟล์แบบ absolute (`/assets/…`) ซึ่งหาไม่เจอเมื่ออยู่ใต้ subpath ส่วน `manifest.webmanifest` ใช้เส้นทางสัมพัทธ์อยู่แล้ว (`start_url`, `scope`, ไอคอน) จึงไม่ต้องแก้ และโค้ดในแอปสร้าง URL เสียงจาก `import.meta.env.BASE_URL` ทุกจุด จึงตามไปเอง

**อย่าแก้ตอนนี้ถ้ายังไม่ได้ทำมิเรอร์จริง** โฮสต์หลักอยู่ที่รากอยู่แล้ว

## 15. ถ้าต้องย้ายไปโฮสต์อื่น

แอปนี้เป็นไฟล์ static ธรรมดา ย้ายไปที่ไหนก็ได้ที่เสิร์ฟไฟล์ผ่าน HTTPS

```bash
git clone <repo>
cd mindful-practice
npm ci
npm run build          # ผลลัพธ์อยู่ใน dist/
find dist -type f -size +25M   # เช็กขนาดไฟล์ถ้าปลายทางมีเพดาน
```

แล้วอัปโหลด `dist/` ทั้งโฟลเดอร์ขึ้นโฮสต์ปลายทาง

**เงื่อนไขของปลายทางมีแค่สามข้อ:**

1. เสิร์ฟผ่าน **HTTPS** — ไม่งั้น service worker, `crypto.randomUUID` และ Screen Wake Lock จะไม่ทำงาน (ดูหัวข้อ secure context ใน `ARCHITECTURE.md`)
2. เสิร์ฟ `.m4a` ด้วย content-type ที่ขึ้นต้นด้วย `audio/` และรองรับ Range request เพื่อให้ Safari เล่นและ seek ได้
3. เสิร์ฟที่รากของโดเมน หรือถ้าอยู่ใต้ subpath ให้ตั้ง `base` ตามข้อ 14

ไม่ต้องมี backend, ไม่ต้องมี database, ไม่มี environment variable, ไม่มี secret และไม่มีขั้นตอนที่ต้องทำด้วยมือนอกเหนือจากนี้
