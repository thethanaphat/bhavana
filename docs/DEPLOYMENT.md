# การ deploy Mindful Practice

เอกสารนี้เขียนให้คนที่ต้องมา deploy หรือดูแลโปรเจกต์นี้ต่อ โดยไม่ต้องถามเจ้าของเดิม

ปรับแผน: 20 กันยายน 2569

## 1. ภาพรวมสถาปัตยกรรม

```
GitHub repository (source of truth)
      │  push เข้า main
      ▼
GitHub Actions  ──npm ci → npm test → npm run build──▶  dist/
      │
      ▼
GitHub Pages  ──▶  https://<username>.github.io/mindful-practice/
      │
      ▼
iPhone / มือถือของผู้ใช้
      │
      ▼
ประวัติการฝึกอยู่ใน IndexedDB ของเครื่องนั้น ไม่มีอะไรถูกส่งกลับมา
```

แอปนี้เป็น **static ล้วน**: ไม่มี backend, ไม่มีฐานข้อมูลฝั่งเซิร์ฟเวอร์, ไม่มี login, ไม่มี analytics, ไม่มีการติดตามผู้ใช้

**เซิร์ฟเวอร์ไม่เก็บข้อมูลผู้ใช้เลยสักอย่าง** ผลที่ตามมาซึ่งสำคัญต่อการตัดสินใจ: ผู้ใช้คนอื่นที่บังเอิญเจอ URL แล้วเข้ามาใช้ **ไม่กระทบข้อมูลของใครทั้งสิ้น** เพราะต่างคนต่างเก็บในเบราว์เซอร์ตัวเอง และเจ้าของแอปก็มองไม่เห็นว่ามีใครใช้อยู่

## 2. บทบาทของ GitHub

GitHub เป็นทั้ง **แหล่งจริงของโค้ด** และ **โฮสต์ production** ใช้เก็บ source code, ประวัติการแก้, เอกสาร, release ที่ติดป้ายเวอร์ชัน และเป็นตัว build กับ deploy ผ่าน GitHub Actions

## 3. ทำไมเลือก GitHub Pages เป็นโฮสต์

เหตุผลหลักไม่ใช่เรื่องราคา แต่เป็น **ความอยู่รอดระยะยาว**

`<username>.github.io` ไม่ต้องต่ออายุ ไม่ต้องจ่ายค่าโดเมน และไม่ผูกกับการที่ธุรกิจของเจ้าของเดิมยังดำเนินอยู่ ต่างจากโดเมนธุรกิจซึ่งจะหยุดทำงานทันทีในวันที่ไม่ได้ต่ออายุ — ซึ่งขัดกับเป้าหมายข้อที่ว่าโปรเจกต์ต้องอยู่รอดแม้ผู้พัฒนาเดิมหยุดดูแล

เหตุผลรอง: เจ้าของโปรเจกต์ใช้ GitHub เป็นประจำอยู่แล้ว การ deploy จึงเป็นแค่ `git push` เหมือนงานอื่น ไม่มีเครื่องมือใหม่ให้ต้องจำ

### ข้อแลกที่ยอมรับไว้แล้ว

- **ต้องใช้ public repository** เพราะ GitHub Pages แบบฟรีเผยแพร่ได้จาก public repo เท่านั้น (private repo ต้องมี GitHub Pro) แปลว่าโค้ดเปิดสาธารณะตั้งแต่วันแรก ซึ่งตรงกับเป้าหมายระยะยาวอยู่แล้ว
- **URL เดาได้** รูปแบบ `<username>.github.io/<repo>/` ใครเปิดหน้าโปรไฟล์ GitHub ก็เห็น สภาพที่ถูกต้องคือ **"เปิดสาธารณะแต่ไม่ได้ประกาศ"** ไม่ใช่ "ไม่มีใครรู้" — ช่วงใช้ส่วนตัวจึงมี `public/robots.txt` กับ `<meta name="robots" content="noindex, nofollow">` ใน `index.html` กันไม่ให้เครื่องมือค้นหาเก็บ index **ลบทั้งสองอย่างเมื่อพร้อมเปิดตัวจริง**
- **เพดาน bandwidth แบบ soft limit ราว 100 GB ต่อเดือน** ดูข้อ 9

## 4. ทำไมไม่ใช้ Railway และไม่ใช้โดเมนธุรกิจ

Railway มีไว้สำหรับแอปที่มี server runtime ทำงานตลอดเวลา แอปนี้ไม่มี backend ให้รันเลย การใช้ Railway จะเพิ่มบิลรายเดือนโดยไม่ได้อะไรกลับมา

หลักการของโปรเจกต์: **"แอปหลักต้องอยู่ได้ต่อไปโดยไม่ต้องมีบิลค่าเซิร์ฟเวอร์รายเดือน"**

เลี่ยงการผูกกับ Railway, ฐานข้อมูลแบบเสียเงิน, เซิร์ฟเวอร์ที่ต้องเปิดตลอด, โฮสต์แบบ subscription, ระบบยืนยันตัวตนฝั่งเซิร์ฟเวอร์, บริการ backend เจ้าของเดียว **และโดเมนที่ต้องต่ออายุ**

ถ้าวันหนึ่งเพิ่มฟีเจอร์ที่ใช้คลาวด์ แอปหลักต้องยังเปิดแอป อ่านบทสวด นั่งสมาธิ เดินจงกรม จับเวลา ดูประวัติและสถิติในเครื่องได้ แม้บริการคลาวด์ล่ม

## 7. ขั้นตอน deploy

ทำครั้งเดียวตอนตั้งต้น:

1. สร้าง repository บน GitHub (public) แล้ว push branch `main` ขึ้นไป
2. ไปที่ repo → **Settings → Pages → Build and deployment → Source: GitHub Actions**
3. เท่านี้จบ — ไฟล์ `.github/workflows/deploy.yml` ในโปรเจกต์จะทำงานเอง

หลังจากนั้นทุกครั้งที่ `git push` เข้า `main` ระบบจะ `npm ci` → `npm test` → `npm run build` → ตรวจขนาดไฟล์ → ปล่อยขึ้น Pages ให้เอง **ถ้า test ตกหรือ type ผิด จะไม่มีอะไรขึ้นเว็บ** สั่งรันเองได้จากแท็บ Actions (workflow_dispatch)

เวอร์ชัน Node อ่านจาก `.node-version` (ตอนนี้ `22.12.0`) **ห้ามลบไฟล์นี้** เพราะ Vite 8 และ TypeScript 7 ต้องการ Node 20.19 ขึ้นไป

ไม่มี environment variable และไม่มี secret ใด ๆ ในโปรเจกต์นี้

### ไม่ต้องตั้ง redirect หรือ rewrite

แอปใช้ **hash routing** (`#/practice/sitting`) ทุกเส้นทางจึงเป็นไฟล์ `index.html` ไฟล์เดียว **การรีเฟรชหรือเปิดลิงก์ลึกจะไม่เกิด 404** ตรวจแล้วทั้งที่รากและใต้ subpath

### เรื่อง base path

`vite.config.ts` ตั้ง `base: './'` ทำให้ build ชุดเดียวใช้ได้ทั้ง:

- ใต้ subpath เช่น `username.github.io/mindful-practice/` (GitHub Pages project site)
- ที่รากโดเมน เช่น `xxx.pages.dev` หรือ `username.github.io` (user site)

`manifest.webmanifest` ก็ใช้เส้นทางสัมพัทธ์ทั้ง `start_url`, `scope` และไอคอน **อย่าเปลี่ยนกลับเป็น path แบบ absolute** เพราะจะล็อกแอปไว้กับตำแหน่งเดียว

## 8. นโยบายไฟล์เสียง

```
public/audio/
  bells/      ระฆังเริ่ม/ระหว่างฝึก/จบ — สั้น ถูก precache
  ambience/   เสียงบรรยากาศและ keepalive — โหลดตอนใช้
  prayers/    เสียงบทสวด — โหลดตอนใช้
```

ชื่อไฟล์เสียงบทสวดมาจาก `content/prayers/catalog.json` ฟิลด์ `audioFile`

**การสร้าง URL รวมไว้ที่เดียวคือ `prayerAudioUrl()` ใน `src/content/audio.ts`** หน้าจอไม่ประกอบ path เองเลย นี่คือเงื่อนไขที่ทำให้ย้ายไฟล์ไป object storage ภายหลังได้โดยไม่ต้องแก้ UI

เสียงระฆังและเสียงบรรยากาศสร้างจาก `scripts/generate_audio.py` (ต้องมี ffmpeg) สคริปต์ seed คงที่ รันซ้ำได้ผลเหมือนเดิมทุกไบต์ ไม่มีไฟล์เสียงจากบุคคลอื่นในโปรเจกต์ เสียงบทสวดเจ้าของโปรเจกต์อัดเอง

## 9. ข้อจำกัดที่ต้องไม่ชน

| ข้อจำกัด | เพดาน | สถานะปัจจุบัน |
|---|---|---|
| ขนาดไฟล์เดี่ยว (Pages ทั่วไป) | 25 MiB | ใหญ่สุด 0.38 MiB |
| ขนาดไซต์รวม (GitHub Pages) | 1 GB | 1.9 MB |
| bandwidth ต่อเดือน (soft) | ~100 GB | — |
| build ต่อชั่วโมง (soft) | 10 | — |

workflow ตรวจขนาดไฟล์ให้อัตโนมัติทุกครั้ง ตรวจเองได้ด้วย `find dist -type f -size +25M` (ไม่มีผลลัพธ์แปลว่าผ่าน)

**การคิดเลข bandwidth:** ตอนนี้ทั้งแอปไม่ถึง 1 MB ต่อการเปิดครั้งแรก และครั้งถัดไปแทบเป็นศูนย์เพราะ service worker → รองรับคนเปิดใหม่ระดับแสนคนต่อเดือน

**แต่เมื่อใส่เสียงบทสวดแล้วเลขนี้เปลี่ยนมาก** ถ้าเสียงสามบทรวม 25 MB และมีคนฟังครบทุกบท จะเหลือราว 4,000 คนต่อเดือน เป็นจุดที่ต้องกลับมาคิดตอนเปิดให้คนอื่นใช้จริง ไม่ใช่ตอนใช้คนเดียว

## 10. ทางหนีเมื่อคนใช้เยอะ หรือเมื่อสื่อใหญ่ขึ้น

**ยังไม่ต้องทำ** เตรียมไว้ให้พร้อมเฉย ๆ

**ถ้าชน bandwidth ของ GitHub Pages** → ย้ายไป **Cloudflare Pages** ซึ่งคำขอไฟล์ static ฟรีไม่จำกัดตราบใดที่ไม่มี Pages Functions ต่อกับ GitHub repo เดิม ตั้ง build command `npm run build` output directory `dist` ใช้ build ชุดเดิมได้ทันทีเพราะ `base: './'` รองรับทั้งรากและ subpath อยู่แล้ว **ห้ามเพิ่ม Pages Functions หรือ Workers** เพราะจะทำให้คำขอปกติกลายเป็นการเรียก Functions ที่มีโควตา

**ถ้าไฟล์เสียงเยอะหรือใหญ่เกิน 25 MiB** → ย้ายสื่อไป object storage เช่น Cloudflare R2

```
GitHub → Pages ─┬─ HTML/CSS/JS/PWA/ข้อความ/ไอคอน/เสียงสั้น
                └─ URL เสียง ──▶ R2
```

วิธีย้าย: อัปโหลดไฟล์ขึ้น R2 แล้วแก้ `audioFile` ใน `catalog.json` เป็น URL เต็ม เช่น `https://media.example.com/itipiso.m4a` — เท่านั้น เพราะ `prayerAudioUrl()` ตรวจว่าขึ้นต้นด้วย `http://` หรือ `https://` ไหม ถ้าใช่คืนค่านั้นตรง ๆ **ไม่ต้องแก้โค้ดหน้าจอสักบรรทัด** อย่าลืมตั้ง CORS ให้อนุญาต origin ของเว็บ เพราะแอปใช้ HEAD request ตรวจว่ามีไฟล์จริงก่อนแสดงตัวเล่น

**ถ้าอยากจำกัดคนเข้าถึงภายหลัง** → ใช้ Cloudflare Access (Zero Trust) วางเป็นด่านหน้า ถามอีเมลแล้วส่งรหัสครั้งเดียว ฟรีในโควตาผู้ใช้จำนวนหนึ่ง **ไม่ต้องแก้โค้ดและไม่ต้องมี backend** อย่าสร้างระบบ login เองเพราะจะลากเซิร์ฟเวอร์รายเดือนกลับเข้ามา

## 11. พฤติกรรม PWA และ offline

Service worker (`public/sw.js`) ลงทะเบียนเฉพาะ production build เพื่อไม่ให้ cache รบกวนตอนพัฒนา

**สิ่งที่ถูก cache ตอนติดตั้ง** — ตรวจจริงแล้วได้ 10 รายการพอดี: `/`, `index.html`, `assets/*.js`, `assets/*.css`, ระฆังสามไฟล์, ไอคอนสองไฟล์ และ `manifest.webmanifest`

**สิ่งที่ไม่ถูก cache โดยตั้งใจ:** ทุกอย่างใต้ `/audio/` ที่ไม่ใช่ระฆัง คือเสียงบรรยากาศและเสียงบทสวด โหลดตอนกดใช้เท่านั้น ข้อความบทสวดถูก bundle เข้าไปใน JS อยู่แล้วจึงอ่านออฟไลน์ได้

ต่อไปถ้าจะให้เก็บเสียงยาวไว้ใช้ออฟไลน์ ให้ทำเป็นปุ่ม **"ดาวน์โหลดไว้ใช้ออฟไลน์"** ที่ผู้ใช้กดเอง ไม่ใช่ precache อัตโนมัติ

**ห้ามถือว่า cache ของเบราว์เซอร์เป็นที่เก็บถาวร** ระบบล้างได้ทุกเมื่อ ข้อมูลผู้ใช้จริงต้องอยู่ใน IndexedDB เท่านั้น

เวลาเปลี่ยนสิ่งที่ cache ต้องขยับเลข `CACHE_NAME` ใน `sw.js` (ตอนนี้ `mindful-practice-shell-v5`) ไม่งั้นเครื่องที่เคยติดตั้งจะใช้ของเก่าต่อ ตัว SW เรียก `skipWaiting()` และ `clients.claim()` แล้ว จึงอัปเดตให้เองเมื่อเปิดแอปครั้งถัดไป

## 12. ข้อมูลผู้ใช้อยู่ในเครื่อง

IndexedDB ชื่อ `mindful-practice` เป็นแหล่งจริงของ `PracticeSession`, `ChantSession`, `ActiveSession`, `Settings`, `LegacyBaseline`, `CustomPrayer` — ไม่มีบัญชีผู้ใช้ ไม่มีการซิงก์

**เบราว์เซอร์ผูกข้อมูลไว้กับ origin** `http://192.168.1.58:4173` กับ `https://username.github.io/mindful-practice/` คือคนละที่เก็บข้อมูลโดยสิ้นเชิง **การย้ายโฮสต์หรือเปลี่ยน URL เท่ากับผู้ใช้เริ่มจากศูนย์** ต้องส่งออกก่อนย้ายเสมอ และถ้าวันหนึ่งย้ายโฮสต์ตอนมีผู้ใช้แล้ว ต้องประกาศล่วงหน้า

## 13. การสำรองข้อมูลด้วย export/import

ในเมนูตั้งค่ามี **ส่งออกเป็นไฟล์ JSON · นำเข้าจากไฟล์สำรอง · ล้างประวัติทั้งหมด**

- รูปแบบ: `{ format: 'mindful-practice-backup', version: 1, exportedAt, settings, practiceSessions, chantSessions, customPrayers, legacyBaseline }`
- ชื่อไฟล์: `mindful-practice-YYYY-MM-DD.json`
- ตัวตรวจไฟล์อยู่ใน `src/data/backup.ts` เป็นฟังก์ชันบริสุทธิ์ ทดสอบได้โดยไม่ต้องมีเบราว์เซอร์
- มีแถวเสียแถวเดียวจะปฏิเสธทั้งไฟล์ ไม่นำเข้าบางส่วนเงียบ ๆ
- นำเข้าคือการแทนที่ทั้งหมด ถามยืนยันพร้อมแสดงจำนวนของเดิมเทียบกับในไฟล์

ผู้ใช้เก็บและย้ายข้อมูลตัวเองได้โดยไม่ต้องพึ่งเซิร์ฟเวอร์และไม่ต้องมีบัญชี

## 14. เวอร์ชันส่วนตัวกับเวอร์ชันสาธารณะ

โปรเจกต์นี้แบ่งการทำงานเป็นสองช่วง: ใช้เองให้เสถียรก่อน แล้วค่อยเปิดให้คนอื่น

**ให้ใช้ codebase เดียวตลอด อย่าแยก repo หรือแยก branch ถาวร** เพราะสองสายจะห่างกันขึ้นเรื่อย ๆ จนการรวมกลับแพงเกินกว่าจะทำ แล้วเวอร์ชันสาธารณะจะไม่เกิดขึ้นจริง

ถ้ามีอะไรที่เป็นของส่วนตัวจริง ๆ ให้ใช้สวิตช์เปิดปิดอันเดียว ไม่ใช่แยกโปรเจกต์ ของที่ต้องเก็บก่อนเปิดสาธารณะตอนนี้มี:

- ตัวเลือก **ระฆังทุก 1 นาที** ซึ่งใส่ไว้ย่นรอบทดสอบ วิธีลบอยู่ในคอมเมนต์ของ `src/data/models.ts`
- `public/robots.txt` และ `<meta name="robots">` ใน `index.html`
- บันทึกระฆังบนหน้าสรุป (`src/features/practice/bellLog.ts`) ซึ่งเป็นเครื่องมือไล่ปัญหา ถอดออกได้ทั้งโมดูลเมื่อมั่นใจแล้ว

## 15. ถ้าต้องย้ายไปโฮสต์อื่น

แอปนี้เป็นไฟล์ static ธรรมดา ย้ายไปที่ไหนก็ได้ที่เสิร์ฟไฟล์ผ่าน HTTPS

```bash
git clone <repo>
cd mindful-practice
npm ci
npm test
npm run build                  # ผลลัพธ์อยู่ใน dist/
find dist -type f -size +25M   # เช็กขนาดถ้าปลายทางมีเพดาน
```

แล้วอัปโหลด `dist/` ทั้งโฟลเดอร์ขึ้นโฮสต์ปลายทาง

**เงื่อนไขของปลายทางมีแค่สามข้อ:**

1. เสิร์ฟผ่าน **HTTPS** — ไม่งั้น service worker, `crypto.randomUUID` และ Screen Wake Lock จะไม่ทำงาน (ดูหัวข้อ secure context ใน `ARCHITECTURE.md`)
2. เสิร์ฟ `.m4a` ด้วย content-type ที่ขึ้นต้นด้วย `audio/` และรองรับ Range request เพื่อให้ Safari เล่นและ seek ได้
3. เสิร์ฟที่รากหรือใต้ subpath ก็ได้ ไม่ต้องแก้อะไร เพราะ `base: './'`

ไม่ต้องมี backend, ไม่ต้องมี database, ไม่มี environment variable, ไม่มี secret และไม่มีขั้นตอนที่ต้องทำด้วยมือนอกเหนือจากนี้
